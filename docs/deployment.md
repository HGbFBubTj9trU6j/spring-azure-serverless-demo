# Deployment

This document describes how to provision and deploy the
spring-azure-serverless-demo application.

The deployment covers:

- Shared Azure infrastructure
- Azure SQL Database
- Spring Boot backend
- React frontend
- Microsoft Entra ID authentication
- Deployment verification

For architectural details, see:

```text
docs/architecture.md
```

For Step 4 data-access implementation details, see:

```text
docs/step04-data-access.md
```

---

## Deployment Overview

The deployment sequence is:

```text
Verify prerequisites and Azure context
        │
        ▼
Provision shared Azure infrastructure
        │
        ▼
Deploy Azure SQL schema and security
        │
        ▼
Build backend OCI image
        │
        ▼
Push image and deploy Azure Container App
        │
        ▼
Build React frontend
        │
        ▼
Deploy frontend to Azure Static Web Apps
        │
        ▼
Configure Microsoft Entra ID authentication
        │
        ▼
Verify the deployed application
```

The deployment scripts load environment-specific non-secret values from:

```text
config/dev.psd1
```

A different environment can be selected when supported by a script.

---

## Administrative Boundaries

The application spans two Microsoft Entra ID tenant contexts.

```text
Azure Subscription Tenant
  │
  ├── Resource Group
  ├── Azure Container Registry
  ├── Azure Container Apps Environment
  ├── Azure Container App
  ├── User Assigned Managed Identity
  ├── Azure Static Web Apps
  └── Azure SQL resources

Authentication Tenant
  │
  ├── App Registration
  └── Service Principal
```

The Azure subscription tenant contains the application infrastructure.

The authentication tenant contains the identity resources used by Azure Static Web Apps authentication.

Always verify the active Azure CLI tenant and subscription before running tenant-specific scripts.

## Required Environment Variables

The developer must prepare the following environment variables when applicable:

```text
ENTRA_TENANT_ID
SWA_DEPLOYMENT_TOKEN
```

### ENTRA_TENANT_ID

`ENTRA_TENANT_ID` is used when generating the Azure Static Web Apps authentication configuration during the frontend build.

Verify that it is defined without displaying its value:

```powershell
if ($env:ENTRA_TENANT_ID) {
    Write-Host "ENTRA_TENANT_ID is configured."
}
else {
    Write-Host "ENTRA_TENANT_ID is not configured."
}
```

### SWA_DEPLOYMENT_TOKEN

`SWA_DEPLOYMENT_TOKEN` is required when deploying the generated frontend to Azure Static Web Apps.

Verify that it is defined without displaying its value:

```powershell
if ($env:SWA_DEPLOYMENT_TOKEN) {
    Write-Host "SWA_DEPLOYMENT_TOKEN is configured."
}
else {
    Write-Host "SWA_DEPLOYMENT_TOKEN is not configured."
}
```

### Build-generated Vite Values

The following values are generated by the frontend build process:

```text
VITE_API_BASE_URL
VITE_BUILD_VERSION
```

They are not prerequisites that normally need to be configured manually.

`VITE_API_BASE_URL` is resolved from the deployed Azure Container App.

`VITE_BUILD_VERSION` is derived from the current Git state.

```text
config/dev.psd1
```

It contains non-secret environment-specific values such as:

## Step 1: Preview Infrastructure Changes

Preview the Bicep deployment before applying it:

```powershell
.\scripts\whatif-infra.ps1
```

Alternatively, run the subscription-scoped What-If operation directly:

```powershell
az deployment sub what-if `
  --name spring-azure-serverless-demo `
  --location japaneast `
  --parameters .\infra\dev.bicepparam
```

Review the proposed resource additions, changes, and deletions before deployment.

The Azure Container App is deployed separately after the backend image is built and is therefore outside the shared-infrastructure deployment path.

Azure-managed properties can appear as modifications in later What-If results even when the Bicep-managed configuration has not changed.

## Step 2: Deploy Shared Azure Infrastructure

Deploy the shared Azure infrastructure:

```powershell
.\scripts\deploy-infra.ps1
```

The subscription-scoped deployment creates or updates the shared resources required by the application.

These resources include:

- Resource Group
- Azure Container Registry
- Azure Container Apps Environment
- User Assigned Managed Identity
- Azure Static Web Apps
- Azure SQL infrastructure
- Required Azure role assignments

The Azure Container App itself is deployed later after the backend OCI image is available.

### Verify Shared Infrastructure

List relevant resources in the Resource Group:

```powershell
az resource list `
  --resource-group spring-azure-serverless-demo-rg `
  --query "[].{Name:name,Type:type,Location:location}" `
  --output table
```

Use the actual Resource Group from the selected environment configuration when it differs from the development example.

## Step 3: Deploy the Database

Deploy the Azure SQL schema, seed data, database principal, and permissions:

```powershell
.\scripts\deploy-database.ps1
```

The script uses the selected environment configuration to resolve the Azure SQL server, database, and Managed Identity names.

Database deployment includes:

- Application schema
- Initial Fortune data
- Managed Identity database principal
- Object-level permissions

The deployed Container App identity receives the permissions currently required on:

```text
dbo.fortunes
```

The expected permissions are:

```text
SELECT
INSERT
DELETE
```

### Verify the Database

Run:

```powershell
.\scripts\verify-database.ps1
```

The verification covers:

- Database connectivity
- Database name and collation
- `dbo.fortunes` table structure
- Managed Identity database principal
- Absence of fixed database role membership
- Object-level permissions on `dbo.fortunes`

The expected object-level permissions are:

```text
DELETE
INSERT
SELECT
```

Detailed database design and verification information is documented in:

```text
docs/step04-data-access.md
```

## Step 4: Build the Backend OCI Image

Build the backend image:

```powershell
.\scripts\build-backend.ps1
```

By default, the script loads:

```text
config/dev.psd1
```

When supported, a different environment can be selected:

```powershell
.\scripts\build-backend.ps1 `
  -Environment prod
```

The build script:

1. Loads environment-specific configuration.
2. Determines the current Git commit.
3. Detects whether the working tree has uncommitted changes.
4. Creates an image tag.
5. Runs the Spring Boot automated tests.
6. Builds the backend OCI image with Spring Boot Buildpacks.
7. Stores the resulting image in the local container runtime.

Example image tags:

```text
<REGISTRY_NAME>.azurecr.io/backend:abc1234
<REGISTRY_NAME>.azurecr.io/backend:abc1234-dirty
```

The `-dirty` suffix indicates that the image was built from a working tree containing uncommitted changes.

### Buildpacks Configuration

The backend image is built with:

```text
Paketo Noble Java Tiny Builder
linux/amd64
```

The build uses a versioned builder rather than relying on a mutable `latest` tag.

The target platform is explicitly configured as:

```text
linux/amd64
```

### Verify the Local Image

List the generated backend images:

```powershell
docker images `
  --format "{{.Repository}}:{{.Tag}} {{.ID}}" |
  Select-String "backend"
```

Inspect the generated image platform and Spring Boot version:

```powershell
docker image inspect `
  <BACKEND_IMAGE> `
  --format "Backend={{.Os}}/{{.Architecture}} SpringBoot={{index .Config.Labels `"org.springframework.boot.version`"}}"
```

The expected deployment platform is:

```text
linux/amd64
```

## Step 5: Deploy the Backend

Deploy the backend image to Azure Container Apps:

```powershell
.\scripts\deploy-backend.ps1
```

By default, the script loads:

```text
config/dev.psd1
```

When supported, a different environment can be selected:

```powershell
.\scripts\deploy-backend.ps1 `
  -Environment prod
```

The deployment script:

1. Loads environment-specific configuration.
2. Determines the image tag from the current Git state.
3. Signs in to Azure Container Registry.
4. Pushes the backend OCI image.
5. Resolves the Container Apps Environment resource ID.
6. Resolves the User Assigned Managed Identity resource ID.
7. Deploys or updates the Azure Container App through Bicep.
8. Displays the deployed image and Container App endpoint.

The same deployment path is used for both initial creation and later backend updates.

### Verify the Deployed Image

```powershell
az containerapp show `
  --name spring-azure-serverless-dev-ca `
  --resource-group spring-azure-serverless-demo-rg `
  --query properties.template.containers[0].image `
  --output tsv
```

### Verify the Container App

```powershell
az containerapp show `
  --name spring-azure-serverless-dev-ca `
  --resource-group spring-azure-serverless-demo-rg `
  --query "{state:properties.provisioningState,fqdn:properties.configuration.ingress.fqdn}" `
  --output table
```

Retrieve the Container App FQDN:

```powershell
$fqdn = az containerapp show `
  --name spring-azure-serverless-dev-ca `
  --resource-group spring-azure-serverless-demo-rg `
  --query properties.configuration.ingress.fqdn `
  --output tsv
```

Verify the random Fortune endpoint:

```powershell
curl.exe "https://$fqdn/api/fortune"
```

Verify the Fortune Management list endpoint:

```powershell
curl.exe "https://$fqdn/api/admin/fortunes"
```

Direct API verification confirms deployed backend functionality.

It is treated as deployed backend feature verification rather than application E2E verification.

## Step 6: Build the Frontend

Before building the frontend, verify that `ENTRA_TENANT_ID` is configured.

```powershell
if (-not $env:ENTRA_TENANT_ID) {
    throw "ENTRA_TENANT_ID is not configured."
}
```

Build the frontend:

```powershell
.\scripts\build-frontend.ps1
```

The frontend build script:

1. Loads the selected environment configuration.
2. Retrieves the deployed Container App FQDN.
3. Sets `VITE_API_BASE_URL`.
4. Determines the current Git commit.
5. Detects whether the working tree is dirty.
6. Sets `VITE_BUILD_VERSION`.
7. Generates the Azure Static Web Apps authentication configuration.
8. Runs the Vite production build.

The generated frontend is written to:

```text
frontend/dist
```

The generated Azure Static Web Apps configuration is written to:

```text
frontend/dist/staticwebapp.config.json
```

Do not manually modify files under:

```text
frontend/dist
```

They are generated build artifacts.

### Verify the Embedded API URL

The generated JavaScript can be inspected to verify the embedded API target.

```powershell
Select-String `
  -Path .\frontend\dist\assets\*.js `
  -Pattern "localhost:8080","azurecontainerapps.io"
```

For an Azure deployment build, the generated artifacts should contain the deployed Container App endpoint.

## Step 7: Deploy the Frontend

Before deploying the frontend, verify that `SWA_DEPLOYMENT_TOKEN` is configured.

```powershell
if (-not $env:SWA_DEPLOYMENT_TOKEN) {
    throw "SWA_DEPLOYMENT_TOKEN is not configured."
}
```

Deploy the generated frontend:

```powershell
.\scripts\deploy-frontend.ps1
```

The deployment script uses Azure Static Web Apps CLI through:

```text
npx @azure/static-web-apps-cli
```

The generated `frontend/dist` directory is deployed to the production environment.

The equivalent deployment operation is:

```powershell
Push-Location .\frontend

try {
    npx @azure/static-web-apps-cli deploy `
      .\dist `
      --env production `
      --deployment-token $env:SWA_DEPLOYMENT_TOKEN `
      --verbose
}
finally {
    Pop-Location
}
```

The deployment explicitly targets:

```text
production
```

Omitting the production environment selection can cause the CLI to deploy to another resolved environment.

### Verify Static Web Apps Environments

```powershell
az staticwebapp environment list `
  --name spring-azure-serverless-demo-dev-swa `
  --resource-group spring-azure-serverless-demo-rg `
  --output table
```

The production environment is represented by:

```text
default
```

After a successful production deployment, its status should indicate that it is ready.

## Step 8: Configure Microsoft Entra ID Authentication

Authentication resources are managed in the authentication tenant.

Azure Static Web Apps application settings are configured in the Azure subscription tenant.

This means the active Azure CLI context must be changed during authentication setup.

### Retrieve the Static Web Apps Hostname

While signed in to the Azure subscription tenant:

```powershell
$swaHostname = az staticwebapp show `
  --name spring-azure-serverless-demo-dev-swa `
  --resource-group spring-azure-serverless-demo-rg `
  --query defaultHostname `
  --output tsv
```

Display the hostname:

```powershell
Write-Host $swaHostname
```

### Switch to the Authentication Tenant

```powershell
az login `
  --tenant <AUTHENTICATION_TENANT_ID> `
  --allow-no-subscriptions
```

Verify the active tenant:

```powershell
az account show `
  --query tenantId `
  --output tsv
```

### Create or Update the App Registration

Run:

```powershell
.\scripts\41-deploy-identity.ps1 `
  -StaticWebAppHostname $swaHostname
```

The script creates or updates:

- App Registration
- Service Principal
- Redirect URI
- ID-token configuration

The Azure Static Web Apps redirect URI follows this form:

```text
https://<STATIC_WEB_APP_HOSTNAME>/.auth/login/aad/callback
```

The existing App Registration is reused when possible.

### Create a Client Secret

Run:

```powershell
.\scripts\42-create-client-secret.ps1
```

If a credential already exists, the script does not create another secret by default.

To create an additional secret:

```powershell
.\scripts\42-create-client-secret.ps1 `
  -CreateNew
```

Existing secret values cannot be retrieved after creation.

Use a newly created secret immediately and do not write it to the repository.

### Switch Back to the Azure Subscription Tenant

```powershell
az login `
  --tenant <AZURE_SUBSCRIPTION_TENANT_ID>
```

Select the target subscription:

```powershell
az account set `
  --subscription <AZURE_SUBSCRIPTION_ID>
```

Verify the active context:

```powershell
az account show `
  --query "{tenantId:tenantId,subscriptionId:id,subscriptionName:name}" `
  --output table
```

### Configure Azure Static Web Apps Authentication

Store the Client ID:

```powershell
$clientId = "<APPLICATION_CLIENT_ID>"
```

Read the newly created Client Secret as a SecureString:

```powershell
$clientSecret = Read-Host `
  "Enter the newly created Client Secret" `
  -AsSecureString
```

Configure Azure Static Web Apps:

```powershell
.\scripts\43-configure-swa-auth.ps1 `
  -ClientId $clientId `
  -ClientSecret $clientSecret
```

A different environment can be selected when supported:

```powershell
.\scripts\43-configure-swa-auth.ps1 `
  -Environment prod `
  -ClientId $clientId `
  -ClientSecret $clientSecret
```

The script verifies that:

- The target Azure Static Web App exists.
- The Application Client ID is configured.
- The secret setting exists.

The Client Secret is not written to a file or displayed by the script.

Detailed authentication information is documented in:

```text
docs/authentication.md
docs/authentication-setup.md
```

## Step 9: Verify the Deployed Application

Retrieve the Azure Static Web Apps production hostname:

```powershell
$swaHostname = az staticwebapp show `
  --name spring-azure-serverless-demo-dev-swa `
  --resource-group spring-azure-serverless-demo-rg `
  --query defaultHostname `
  --output tsv

Write-Host "https://$swaHostname"
```

Open the displayed URL in a browser.

Verify authentication behavior:

- Unauthenticated access starts the configured authentication flow.
- A registered user can sign in.
- An unregistered user is denied access.
- The application is displayed after authentication.
- Logout completes successfully.

Verify the application:

- The frontend build version is displayed.
- A random Fortune can be retrieved.
- Existing Fortune records are displayed in Fortune Management.
- A Fortune can be added.
- The added Fortune appears in the management list.
- The added Fortune can be deleted.
- The deleted Fortune disappears from the management list.

The Fortune Management verification is a user-scenario verification through the deployed application.

Direct API calls alone are not treated as the application E2E scenario.

Detailed testing and verification definitions are documented in:

```text
docs/testing.md
```

Step 4-specific verification details are documented in:


## Frontend-only Redeployment

When only the frontend changes:

1. Verify `ENTRA_TENANT_ID`.
2. Rebuild the frontend.
3. Verify `SWA_DEPLOYMENT_TOKEN`.
4. Deploy the generated frontend.

```powershell
.\scripts\build-frontend.ps1
.\scripts\deploy-frontend.ps1
```

Backend and database deployment are not required when their deployed configuration has not changed.

---

## Backend-only Redeployment

When only the backend changes:

1. Run backend tests.
2. Build the backend OCI image.
3. Push and deploy the backend.
4. Verify deployed backend functionality.

```powershell
.\scripts\build-backend.ps1
.\scripts\deploy-backend.ps1
```

If the backend API contract changes, rebuild and redeploy the frontend when required.

---

## Database-only Redeployment

When only database scripts or permissions change:

```powershell
.\scripts\deploy-database.ps1
.\scripts\verify-database.ps1
```

Review database changes carefully before applying them to a non-development environment.

---

## Full Redeployment

For a complete rebuild of the application environment, follow this order:

```text
1. Deploy shared Azure infrastructure
2. Deploy and verify the database
3. Build the backend image
4. Deploy the backend
5. Build the frontend
6. Deploy the frontend
7. Configure or verify authentication
8. Verify the deployed user scenario
```

The corresponding primary commands are:

```powershell
.\scripts\deploy-infra.ps1

.\scripts\deploy-database.ps1
.\scripts\verify-database.ps1

.\scripts\build-backend.ps1
.\scripts\deploy-backend.ps1

.\scripts\build-frontend.ps1
.\scripts\deploy-frontend.ps1
```

Authentication scripts are executed as required for the target Azure Static Web Apps environment.

## Secret Handling

Do not commit:

- Client secrets
- Azure Static Web Apps deployment tokens
- Access tokens
- Refresh tokens
- Azure credentials
- SQL credentials
- Private certificates or keys
- Environment-specific generated authentication files

Use appropriate secret storage such as:

- Azure Static Web Apps application settings
- GitHub Actions secrets
- Azure Key Vault
- Local user environment variables

Generated files under `frontend/dist` must not be committed.
